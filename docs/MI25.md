# Kindi on the AMD Instinct MI25 (gfx900) — experimental port

Status: **compiles for gfx900; not yet run on hardware.** `kindi verify` (token-exact against llama.cpp) is the gate.

## What changed and why

| Problem on gfx900 | Fix |
|---|---|
| Vega is **wave64**; Kindi's kernels are written for 32-lane warps. `__shfl(v, lane)` with the default width (64) makes the upper half of a wave read the lower half's lanes (e.g. `KSHFL(wv[i], 26)` in the q8 attention kernel). | The portability macros `KSHFL` / `KSHFLX` now pass `width = 32`, so each 64-lane wave behaves as two 32-lane warps. On RDNA3 (wave32) the code generated is the same. xor offsets in the kernels are all ≤ 16, and there is no ballot/activemask use. |
| `__builtin_amdgcn_sudot4` (`v_dot4_i32_iu8`) exists only on gfx11+. The gfx900 build failed. | `kdp4a` / `g4_dp4a`: gfx11/12 use `sudot4`, gfx906/908/90a use `sdot4`, everything else (gfx900) uses the portable 4-multiply path. |
| RDNA3 WMMA kernels (Nemotron prompt GEMM) | Already compiled only for gfx110x; Python falls back to the dp4a path. Nothing to do. |
| `KINDI_TC=1` (tc_hip.cu) | RDNA3 only (sudot4 + wave32 layout). **Leave `KINDI_TC` off on the MI25.** |
| CuPy's precompiled parts were built for RDNA3 only | `Dockerfile.rocm` takes `--build-arg AMDGPU_TARGETS=gfx900`. |

Checked offline with `hipcc --offload-arch=gfx900` and `gfx1100` (Ubuntu's HIP 5.7): `kindi.cu`, `gemma4.cu`, and the
composed chunk module (kindi.cu + wrappers + chunk.cu + chunk1.cu) all build for both targets.

## Known risks (in order)

1. **ROCm 6.3 userland on gfx900.** AMD dropped gfx900 from the official support list. The runtime and compiler still
   contain it, but AMD's rocBLAS packages may not. Kindi's Bonsai path does not use BLAS except the optional
   `fast-head` build, so use `KINDI_HEAD=exact`. If ROCr itself refuses the card, fall back to Ubuntu's ROCm packages
   (Ubuntu/Debian build rocBLAS etc. for gfx900; confirmed in noble's `librocblas0`).
2. **PCIe atomics.** Vega 10 compute needs AtomicOps from the root port. The x16 slot (CPU) is fine. Cards on chipset
   or x1 paths may be skipped by KFD (`dmesg | grep kfd`). `mi25-bringup.sh check` shows it.
3. **Hidden wave32 assumptions** the compiler can't see (implicit lockstep across exactly 32 threads with shared
   memory). `verify` on the 2B, then the 27B, will catch these as token mismatches.

## Bring-up

```bash
scripts/mi25-bringup.sh check
scripts/mi25-bringup.sh build
scripts/mi25-bringup.sh models
scripts/mi25-bringup.sh verify 0000:XX:00.0 2b
scripts/mi25-bringup.sh verify 0000:XX:00.0 27b
scripts/mi25-bringup.sh bench  0000:XX:00.0 27b
```

Then try `KINDI_CHUNK_Q8=0` (fp32 prompt path) against the default int8 path: without hardware dp4a, fp32 may read
prompts faster on Vega.
