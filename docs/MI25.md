# Kindi on the AMD Instinct MI25 (gfx900)

Status: **runs and verifies on hardware.** On an MI25 (V320 firmware, 110 W cap) in a PCIe Gen3 x16 slot, with AMD's
ROCm 6.3.3 image, `kindi verify` passes 4/4 token-exact against llama.cpp for the 2B and the 27B. The gfx900 defaults
below are the measured best. Baseline tag: `mi25-gfx900-bonsai27b-baseline-2026-11-01`; data in `docs/mi25-results/`,
scripts in `scripts/mi25-lab/`.

## What changed and why

| Problem on gfx900 | Fix |
|---|---|
| Vega is **wave64**; Kindi's kernels are written for 32-lane warps. `__shfl(v, lane)` with the default width (64) makes the upper half of a wave read the lower half's lanes (e.g. `KSHFL(wv[i], 26)` in the q8 attention kernel). | The portability macros `KSHFL` / `KSHFLX` pass `width = 32`, so each 64-lane wave behaves as two 32-lane warps. On RDNA3 (wave32) the code generated is the same. xor offsets in the kernels are all ≤ 16, and there is no ballot/activemask use. |
| `__builtin_amdgcn_sudot4` (`v_dot4_i32_iu8`) exists only on gfx11+. | `kdp4a` / `g4_dp4a`: gfx11/12 use `sudot4`, gfx906/908/90a use `sdot4`, everything else (gfx900) uses the portable 4-multiply path. |
| Chunked prefill is off on HIP by default (it needs the lane-table weights, `KINDI_G5L=1`, which HIP leaves off). Prefill then reads one token at a time: 12.3 tok/s on the 27B. | `gpudrv.wave64_no_dot()` detects gfx8/gfx900 and defaults `KINDI_G5L=1` and `KINDI_CHUNK_Q8=0` (fp32 chunk products; no hardware dp4a). Both variables still override. |
| RDNA3 WMMA kernels (Nemotron prompt GEMM) | Compiled only for gfx110x; Python falls back to the dp4a path. |
| `KINDI_TC=1` (tc_hip.cu) | RDNA3 only. **Leave `KINDI_TC` off on the MI25.** |
| CuPy's precompiled parts were built for RDNA3 only | `Dockerfile.rocm` takes `--build-arg AMDGPU_TARGETS=gfx900`. |

## Measured (27B, x16 MI25, q8_0 K/V)

| Configuration | Prefill tok/s | Decode tok/s |
|---|---|---|
| Upstream HIP defaults (before the lane-table files exist) | 12.3 | 11.8 |
| gfx900 defaults (`G5L=1`, `CHUNK_Q8=0`) | 67.0 (2,048-token prompt) | 15.1 or 13.9 (see below) |

Variance sweep (5 rounds × 6 configurations, order rotated; `sweep.csv`): `CHUNK_Q8=0` gives a real +2.6% prefill (no
overlap, ranges ≤ 0.1 tok/s). `KINDI_DP4A` has no effect on gfx900 (the "dp4a" there is the software path). `G5L=1`
lifts decode from 11.8.

## Known issue: two decode states

Decode with `G5L=1` lands in one of two states per launch, 15.11 ± 0.03 or 13.93 ± 0.02 tok/s (ratio 0.922), fixed at
start-up and independent of the configuration. Prefill is not affected. llama.cpp on the same card has one state.

- **Not the clocks:** with the HBM clock pinned at 945 MHz the split remains (`twostate.csv`). Power (at the 110 W cap) and
  temperature are the same in both states. The core clock reaches 1,500 MHz only in slow launches — an effect: the
  weight kernel stalls, power drops, the governor clocks up.
- **One kernel:** rocprofv3 traces (`profile-fast-vs-slow.txt`) put the whole difference in `k_g5n4`, the 5-trit
  lane-table weight GEMV (×1.091). Every other kernel is slightly faster in the slow state. GPU busy time is the same.
- **Not visible at allocator-summary level:** the weights are one 5,340 MiB buffer, 2 MiB-aligned, in every launch; the
  amdgpu buffer flags and buddy free lists are the same in fast and slow launches (`vram-dumps.txt`).
- **Allocation history shifts the odds:** a dummy allocation held while the weights load raises the fast share from
  13/25 (52%) to 21/25 (84%) for 4 GiB (p = 0.032) and 51/65 (78%) for any dummy (p = 0.019), over 90 idle-checked
  launches (`perturb-run1.csv`, `perturb-run2.csv`) — but never makes it deterministic.

- **Fixed per process, not per allocation:** rebuilding the engine inside one process never changed the state — 40
  builds in 10 processes (5 fast, 5 slow), including rebuilds with 1 GiB held to move the weights
  (`selfcheck-probe.log`, `scripts/mi25-lab/selfcheck_probe.py`). Something set up once per process (hardware queue,
  VM context or similar runtime state) decides it, together with how `k_g5n4` reads the weights; the physical location
  of the weights alone does not.

Open: identify that per-process state (`umr`, queue/VMID inspection), or make `k_g5n4` insensitive to it.

### Start-up self-check (`KINDI_SELFCHECK_TPS`)

`kindi/selfcheck.py`: after the engine is built, the server times 48 greedy decode steps (~3 s). Below the threshold it
re-executes itself (`os.execv`, same container and port) to draw a new state, up to `KINDI_SELFCHECK_TRIES` (default 5;
the last attempt is kept). Off unless `KINDI_SELFCHECK_TPS` is set. For the 27B on the MI25 use `14.6` (slow 14.1–14.2,
fast 15.15 in this check). A retry costs ~20 s of start-up. Tested: a slow start (14.21) re-executed and came up at
15.15; through llama-swap, starts take ~20–40 s.

## Bring-up

```bash
scripts/mi25-bringup.sh check                 # ROCm agents, PCIe links, Docker (no sudo needed)
scripts/mi25-bringup.sh build                 # kindi-rocm:mi25 (ROCm 6.3.3 + CuPy for gfx900)
scripts/mi25-bringup.sh models                # 2B + 27B, sha256-checked, converted
scripts/mi25-bringup.sh verify 0000:XX:00.0 2b
scripts/mi25-bringup.sh verify 0000:XX:00.0 27b
scripts/mi25-bringup.sh bench  0000:XX:00.0 27b
```

`bench`'s "prompt reading" line feeds one token at a time; `scripts/pp_bench.py` measures the real (chunked) prefill.
The first start writes the 5-trit weights (~4.5 min for the 27B); later starts take ~9 s. All three MI25s on the test
host were usable ROCm agents, including two behind the B550 chipset on x1 links.
